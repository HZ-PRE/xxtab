# 已导入配置的实际网络检测（2026-09-16）

## 结论及配置处理

在用户这台 Windows 主机，通过其已导入配置连接 Cloudflare → nginx → wstunnel → WireGuard，测试用户指定的 `10.10.25.202:8889` 网页。WireGuard 成功握手，内网路由实际走 `xxtab0`。未提交登录表单、修改远端配置或扫描网段。

主要等待发生在网络往返及资源传输。当前证据不能进一步区分客户端到 CDN、CDN 到原站、原站到内网各段的贡献。小样本参数对比没有显示稳定收益，因此保留用户原配置：MTU 1280、默认 balanced、DNS 自动解析入口。没有把测试配置设为用户配置，也没有修改原站/CDN。

测试前未连接隧道，所有临时会话到期后正常卸载 WireGuard 服务和其添加的绕行路由，恢复原先未连接状态。

## 外层及内网延迟

外层两个 DNS 返回的 IPv4，各测 5 次，保留域名进行 TLS 证书校验：

| 入口 | TCP 建连 | TCP + TLS 建连 |
| --- | --- | --- |
| 172.67.182.85 | 201–222 ms | 411–447 ms |
| 104.21.32.25 | 201–233 ms | 415–770 ms |

首次 DNS 查询耗时 227 ms；它不是每个内网数据包的开销。

以下网页请求均新建 TCP 连接，记录入口第一次 HTTP 302 响应的首字节时间；这是网页入口响应，**不是完整页面或浏览器渲染完成时间**。各轮是顺序测试，公网状态可能变化，不能将小差异归因于参数。

| 参数/轮次 | 请求数 | TCP 中位数 | 首字节中位数 |
| --- | --- | --- | --- |
| balanced / MTU 1280，首轮 | 8 | 394.1 ms | 791.6 ms |
| interactive / MTU 1280，首轮 | 8 | 394.6 ms | 785.2 ms |
| balanced / 第二 CDN 入口 | 8 | 422.1 ms | 844.2 ms |
| balanced / MTU 1280，复测 | 8 | 393.0 ms | 784.2 ms |
| balanced / MTU 1420 | 8 | 407.0 ms | 814.6 ms |
| interactive / MTU 1280，复测 | 4 | 403.6 ms | 807.0 ms |

首轮 ICMP：10 次中 9 次在 1 秒内回复，成功回复 389–608 ms，均值 416 ms；一次超时不能据此推断长期丢包率。interactive 轮次 15 次全部在 1.5 秒内回复，389–589 ms。第二入口 15 次全部回复，418–692 ms。MTU 1420 下 1392 字节 DF ICMP 载荷的 3 次探测均收到回复，但未看到提速证据。

## 网页资源下载

保留入口重定向所需 Cookie 后能得到 HTTP 200 的 430 字节页面壳，随后加载约 1.66 MB JavaScript 与 104 KB CSS。测试仅访问页面引用的同源静态资源，不执行页面脚本。首轮未携带 Cookie 的资源请求失败，已从资源速度对比中排除。

未压缩 JS，含建连与等待、并发下载 CSS 时：

| 参数 | JS 字节数 | 完整下载时间 |
| --- | --- | --- |
| balanced / MTU 1280 | 1,659,242 | 9.38 s |
| balanced / 第二 CDN 入口 | 1,659,242 | 6.91 s |
| balanced / MTU 1420 | 1,659,242 | 9.29 s |
| interactive / MTU 1280 | 1,659,242 | 10.93 s |

这些是每种设置一次的短文件测试，不足以证明吞吐差异来自设置；第二入口虽然本次资源下载更快，但稳定的基础延迟更高，未固定该入口。

另外在默认入口/balanced/MTU 1280 下，串行测试同一个 JS：gzip、identity、gzip。服务端已支持 gzip，结果为：

| 编码 | 实际传输字节 | 完整下载时间 | 含建连的有效速率 |
| --- | --- | --- | --- |
| gzip | 477,350 | 3.59 s | 1.06 Mbps |
| identity | 1,659,242 | 5.20 s | 2.56 Mbps |
| gzip | 477,350 | 3.38 s | 1.13 Mbps |

压缩降低字节数与等待时间。短文件受 TCP 慢启动、往返时延和抖动影响，这些有效速率**不是线路带宽上限**，也不能把 identity 请求等同于真实浏览器加载；浏览器通常会请求压缩资源。响应未观察到 Cache-Control / ETag，服务端可进一步核实静态资源缓存策略，但未在本次更改该网站。

## 客户端资源和排队

低负载时 WS Ping/Pong 通常约 388–420 ms；下载期间曾出现约 680–960 ms 的样本。它是 WebSocket 心跳 RTT，不能独立证明每一段网络延迟。

各次会话应用队列等待最大约 2.1 ms，已完成写入最大约 0.5 ms；所有会话退出累计应用丢包 0、重连 0。这不表示底层 TCP 没有重传，也不能排除内核或远端队列。

一次进程快照：测速转发进程工作集约 8.1 MiB，私有内存约 1.4 MiB；已打开 GUI 工作集约 18.2 MiB。不是峰值统计，也不包含系统 WireGuard 服务、驱动及网络栈内存。目前无证据表明客户端内存或应用队列造成数百毫秒延迟。

## 下一步

需要用户提供 wstunnel 原站公网 IP、直连端口及是否只允许 Cloudflare 访问。可用配置副本的 `server_ip` 绕过 CDN 测量，保留原域名做 TLS 校验；若使用 Cloudflare Origin CA，需要配置可信 CA 文件，不能关闭证书校验。当前未获取原站信息，未做这一对比。

若直连明显更快，再考虑原站直连、改用更近的中转节点，或在网络条件允许时使用原生 WireGuard UDP。客户端参数无法消除当前路径约 390–420 ms 的基础往返时间。

## 可复测工具

- `examples/timed_session.rs`：限时真实隧道会话，正常到期或 Ctrl+C 会清理所管理的服务和路由；最大 600 秒。不应强杀进程。
- `tools/measure-http.py`：同源网页及最多 8 个静态资源检测，每个响应最多读取 2 MiB；不输出 URL、Cookie 或响应正文，不使用环境 HTTP 代理。输出可能截断的资源会标注 `limit_reached`。小文件结果只用于响应和短下载对比。
- `live-network-results-2026-09-16.json`：各轮原始 HTTP 时间/字节结果，无私钥、路径密钥或 Cookie。
