# 2026-09-15 性能优化记录

优化了客户端的发送分配、TLS 写入和单线程收发调度。32 包突发的本机 WS/WSS 回显测试有稳定收益；128 包极端突发仍超过链路中的处理能力，端到端丢包没有改善。复用缓冲降低了分配频率，但实测进程内存略有增加。

## 实现

- 33 个可重复使用的 2048 字节缓冲：最多 32 包排队、一个包正在写入，替代每包 `to_vec()` 分配和释放。
- 当前已到达的数据最多 16 帧合批，使用 16 KiB 写缓冲，批末刷新 TLS。每帧仍是一个独立 UDP 数据报；单包立即刷新，不使用等待凑批的定时器。
- 收发各处理最多 16 包便让其他任务运行；替换来源地址和接收时间的互斥锁为当前线程内部状态。保持单线程运行时。
- 排队期限由 250 ms 缩短为 100 ms，保持 32 包容量。发生拥塞时每 5 秒汇总应用队列满和过期丢包；不为每包写日志。
- 保留 TLS 证书验证、TCP_NODELAY、报文大小限制、来源固定、自动重连及退出清理。

## 测量方法

Windows x64，Rust 1.92.0 release，官方 wstunnel v10.7.1。客户端、服务端及 UDP 回显器均运行在同一台机器。旧版和最终优化版交替运行三轮；最终三轮没有并行编译或其他测试任务。现有用户窗口保持运行，因此仍可能存在普通桌面负载和调度波动。

链路为测试发送器 → xxtab relay → 官方 wstunnel → UDP 回显器 → 原路返回。这里不包含真实 WireGuard 加密或公网链路的吞吐；真实 WireGuard 另做功能验证。

每包 1280 字节；每轮单包场景 5000 包，32 包突发场景 160,000 包，128 包突发场景 25,600 包。每批连续发送后收取回显，无重传；读取超时为 30 ms，Windows 实际超时可能更长。负载发生器和回显器的接收缓冲设为 1 MiB，产品使用系统默认 UDP 缓冲。校验收到的每包内容、序号、重复包及报文边界。

吞吐按成功返回的有效载荷计算，只计一个方向的字节数。延迟从批次开始发送计到每包返回；P99 只统计收到的包，丢失单独报告。下表为各轮指标的中位数，丢包率为三轮合计。

## 结果

| 场景 | 吞吐：旧版 → 优化版 | P99：旧版 → 优化版 | 端到端丢包：旧版 → 优化版 |
| --- | --- | --- | --- |
| WS，单包 | 96.7 → 102.8 Mbps | 0.246 → 0.218 ms | 0 → 0 |
| WSS，单包 | 90.1 → 97.0 Mbps | 0.270 → 0.260 ms | 0 → 0 |
| WS，32 包突发 | 329.8 → 440.8 Mbps | 1.355 → 0.947 ms | 0 → 0 |
| WSS，32 包突发 | 271.8 → 392.1 Mbps | 1.731 → 1.067 ms | 0 → 0 |
| WS，128 包突发 | 17.4 → 18.3 Mbps | 21.831 → 23.931 ms | 33.21% → 34.30% |
| WSS，128 包突发 | 17.8 → 17.2 Mbps | 25.095 → 25.186 ms | 32.31% → 35.36% |

32 包 WSS 场景吞吐提高约 **44%**，P99 降低约 **38%**；完成相同 160,000 包任务，客户端 CPU 时间中位数从 **0.516 秒降到 0.234 秒**，约降低 55%。CPU 时间来自 Windows GetProcessTimes，短任务的计时粒度有限；某些单包测试读到零不表示没有 CPU 开销。

128 包场景不能声称优化成功：WSS 回显器实际收到的包中位数从 17,970/25,600（70.2%）提高到 25,550/25,600（99.8%），说明上行突发转发有明显改善，但到达回显器后仍在回程大量丢失，最终丢包反而有所增加。现有测试没有进一步定位到具体的回程套接字或服务端队列。增加本地 UDP 接收缓冲的试验未消除该现象，发布版本没有增加这项内存开销。不能把上行改进表述为整个代理已经无丢包。

## 内存

三轮负载完成后的 CLI 进程快照范围（MiB，非峰值）：

| 进程指标 | 旧版 | 优化版 |
| --- | --- | --- |
| WS 工作集 | 6.07 | 6.16–6.40 |
| WS 私有提交 | 1.35 | 1.41–1.67 |
| WSS 工作集 | 6.61 | 6.77–6.88 |
| WSS 私有提交 | 1.36–1.38 | 1.54–1.66 |

内存优化体现在消除本地 UDP 发送路径的逐包分配、复用有界存储，**不是降低了这次测量中的进程内存**。复用池载荷容量约 66 KiB，写缓冲 16 KiB；没有无限增长的队列。库、系统分配器和内核还会占用额外内存。上述数据不包括 Windows 界面、WireGuard 服务、驱动及内核缓冲，也不是长期压力测试。

本次 Windows CLI 为 2,401,792 字节，GUI 为 2,521,088 字节，约 2.29 / 2.40 MiB。

## 验证和复现

已通过 Windows 普通测试及 Clippy；新增测试验证复用指针、队列容量、FIFO、取消等待后的唤醒、批次上限、单包及时刷新及过期包丢弃。官方 WS/WSS 互通验证报文边界、超大包、来源固定、心跳、服务器重启重连、不可信 TLS 拒绝。Windows 原生界面连接／重连／断开／关闭清理测试通过。Linux/WSL 构建、真实 WireGuard 握手、加密 ICMP 通信和 SIGTERM 路由及接口清理通过。

在 Windows 配好 OpenSSL 和官方 wstunnel 后：

```powershell
$env:WSTUNNEL_BIN = 'C:\tools\wstunnel.exe'
$env:XXTAB_BIN = (Resolve-Path .\target\release\xxtab.exe).Path
cargo test --test interop official_load -- --ignored --nocapture --test-threads=1
```

测试是观测工具，对过载丢包进行报告，不把零丢包作为负载测试通过条件；功能正确性由报文校验和独立测试验证。
